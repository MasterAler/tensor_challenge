# SQLite hierarchy

Всё в одном скрипте `hierarchy.sql`: таблица, индексы, тестовые данные и поисковый запрос в конце. Поисковая фраза задаётся в CTE `search`, в приложении там будет параметр.

## Как запустить

```bash
sqlite3 :memory: < hierarchy.sql
```
или выполнить в любом клиенте. Нужен SQLite не старее 3.35 (generated columns и `MATERIALIZED`), проверял на 3.50.

## Особенности решения

- иерархия -- обычный adjacency list, `parent_id` со ссылкой на ту же таблицу. Отдельный признак "раздел/элемент" заводить не стал, разделом элемент делает наличие детей, вложенность любая. Materialized path или closure table тут показались лишними, рекурсивного CTE хватает

- по заданию сначала было похоже, что всё решается через `COLLATE NOCASE` + `LIKE 'това%'`, первая версия так и была написана. Но кириллица прямо в примере, а `NOCASE`, `LIKE` и `lower()` в SQLite с регистром нормально работают только для ASCII, `'Товар' LIKE 'това%'` -- это 0. Так что был повод показать что-то интересное =))

- "правильный" путь -- ICU (юникодные `lower()` и сопоставления-коллации), он мне известен, но в рамках тестового это гемор: в стандартных сборках его нет, проверяющему пришлось бы собирать расширение. Вспомнил старый трюк, который когда-то видел: нормализованный ключ через `lower()` + цепочку `replace()` по русскому алфавиту. Некрасиво, зато работает в любом SQLite. Ну и да, можно было бы зарегистрировать свою `lower()`, но это мне придётся Python/C++ прилагать или что-то подобное, так ещё хуже, сказано же явно SQL-скрипт предоставить.

- ключи `name_key` / `short_key` сделаны `GENERATED ... STORED`, считаются один раз при записи и лежат на диске как обычные колонки, приложению про них знать не надо. Индексы строятся по ним, поиск с начала строки -- диапазон `key >= q AND key < q || U+10FFFF`, это `SEARCH ... USING INDEX`, без перебора таблицы (проверял `EXPLAIN QUERY PLAN`). Два условия через `OR` SQLite разворачивает в MULTI-INDEX OR по обоим индексам

- запрос: `found` -- совпадения, `up` поднимается от них к корням через первичный ключ (`UNION`, так что общие предки не дублируются), `tree` спускается обратно от корней только по найденному подмножеству, чтобы посчитать уровень и путь для сортировки. Для спуска нужен индекс на `parent_id`, он же пригодится для внешнего ключа

- сортировка по пути из ключей имён, так что дети идут сразу за родителем, а соседи -- по имени без учёта регистра. В сегмент пути добавлен `id`, иначе два одноимённых раздела под одним родителем перемешали бы своих детей. Одинаковые "Вторичный товар" из разных корней не смешиваются в любом случае, они под разными корнями

- в результате `id`, `parent_id`, `level`, колонка `tree` с отступами (для глаз) и флаг `found` -- найден ли элемент сам или попал как предок

- в тестовых данных кроме примера из задания: уровень 3, элемент, найденный только по короткому имени, "товар без номера" строчными (проверка сортировки), и пара "Услуг", которые находиться не должны
